> 资料状态：2026-08-27。所有容量使用十进制 GB/TB，另有说明时才使用 GiB/TiB；所有链路带宽都注明单向或双向。

过去把 AI 服务器抽象成“8 张 GPU + 一块 NVSwitch 底板”通常够用。到了 2026 年，这个模型会漏掉真正决定性能的系统边界：GPU 已经跨越服务器机箱，在整个液冷机架内形成 scale-up fabric。

“72 GPU 机架”也很容易被误解成 72 卡共享内存服务器。它实际上同时存在四个边界：

1. **故障与操作系统边界**仍是计算节点；
2. **GPU 内存访问边界**被 NVLink 和 IMEX 扩展到机架；
3. **集合通信边界**可以覆盖 72 GPU，但性能取决于消息、算法和软件；
4. **部署边界**变成 100kW 以上的供电、液冷和整架网络。

本文先拆开 NVIDIA GB300 NVL72，再用 AMD Helios 对照。重点不是背规格，而是解释每个数字怎样产生、解决了什么问题，又没有解决什么问题。

## 1. 先把“72”拆成可以审计的物理结构

GB300 NVL72 的参考架构由下列主要部件构成：

```text
18 × compute tray
  ├─ 4 × B300 GPU
  ├─ 2 × Grace CPU
  ├─ 4 × ConnectX-8 HCA
  ├─ 1 × BlueField-3 DPU
  └─ 本地启动盘 / 缓存盘

 9 × NVLink switch tray
  └─ 2 × NVSwitch ASIC

合计：72 GPU + 36 CPU + 72 HCA + 18 NVSwitch ASIC
```

所以 72 不是神秘的营销数字，而是：

```text
18 compute trays × 4 GPU/tray = 72 GPU
9 switch trays × 2 NVSwitch/tray = 18 NVSwitch
```

每张 B300 有 18 条 NVLink 5，每条连到一个不同的 NVSwitch。于是每张 GPU 与机架内全部 18 个交换 ASIC 都有直接链路，交换层没有传统叶脊网络那样的第二跳。

```text
GPU 0 ─┬─ NVSwitch 0
       ├─ NVSwitch 1
       ├─ ...
       └─ NVSwitch 17

GPU 1 ─┬─ NVSwitch 0
       └─ ... 同样 18 条链路
```

这里的“单跳”指 GPU 发出的 fabric 流量只经过一个 NVSwitch ASIC 到达目标 GPU；并不表示一次远端访问与本地 HBM 延迟相同。

官方组件表给出的每 GPU NVLink 双向聚合带宽是 1.8 TB/s，推导很直接：

```text
18 links/GPU × 100 GB/s/link（双向合计） = 1.8 TB/s/GPU
72 GPU × 1.8 TB/s/GPU = 129.6 TB/s ≈ 130 TB/s/rack
```

**130 TB/s 是把所有端口收发线速相加的机架聚合口径。**它不是单个进程能获得的带宽，也不是 AllReduce 的 `algbw`。真实值还要扣除协议开销、路径冲突、操作粒度、归约算法、同步和 GPU 内核效率。

同理，B300 每卡 288 GB HBM3e、最高 8 TB/s，因此整架是：

```text
72 × 288 GB = 20,736 GB = 20.736 TB HBM
72 × 8 TB/s = 576 TB/s HBM 聚合峰值
```

这两个乘法只说明**总容量**与**全部通道同时工作的理论带宽**。它们不意味着任意 GPU 可以用 576 TB/s 扫描全部 HBM。

数据依据：[NVIDIA NVL72 组件说明](https://docs.nvidia.com/enterprise-reference-architectures/nvl72-ai-factory/latest/components.html)与 [Blackwell Ultra 架构说明](https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era/)。

## 2. 72 GPU 为什么不是“一个超大 NUMA 服务器”

判断系统边界，不能只看 GPU 之间能否 P2P。至少要问三个问题：

| 问题 | GB300 NVL72 的答案 |
|---|---|
| 是否只有一个 OS kernel？ | 否。机架包含多个可独立运行的计算节点/OS 域。 |
| 是否存在一个硬件自动一致的 20.7TB HBM 地址空间？ | 否。每张 GPU 仍拥有自己的物理 HBM。 |
| 一个 CUDA 进程能否访问其他节点导出的 GPU 内存？ | 能，但需要 Fabric Manager 与 IMEX 建立映射和权限。 |

### 2.1 本地虚拟地址怎样变成远端 HBM 访问

多节点 NVLink 的关键不只是物理线缆，而是地址和权限控制。简化后的数据路径如下：

```text
CUDA virtual address
  → local GPU page-table translation
  → fabric address / target GPU
  → NVLink 5
  → NVSwitch
  → remote GPU HBM physical address
```

IMEX（Internode Memory Exchange）负责把某段 GPU 内存安全地导出、分发共享句柄，再由另一节点的进程导入。Fabric Manager 配置内存 fabric；NVLSM 发现拓扑、分配 LID 并写入交换转发表。

控制面和数据面是两条不同路径：

- IMEX daemon 的会话、鉴权和句柄交换走 TCP/gRPC 控制网络；
- 真正的远端 load/store/atomic 数据走 NVLink 背板；
- IMEX 或 fabric 初始化失败时，机内 GPU 可能正常，跨节点 NVLink 作业仍会失败。

这解释了一个重要现象：`nvidia-smi` 能看到 72 张健康 GPU，并不能证明 72-GPU CUDA 作业已经具备正确的远端内存语义。

参考：[NVIDIA IMEX Overview](https://docs.nvidia.com/multi-node-nvlink-systems/imex-guide/overview.html)和 [Multi-Node NVLink System Guide](https://docs.nvidia.com/multi-node-nvlink-systems/mnnvl-user-guide/overview.html)。

### 2.2 能寻址，不等于应该把远端 HBM 当本地内存

远端访问仍有额外延迟和争用。软件通常采用以下策略：

- 权重和 KV 数据尽量放在消费它的 GPU 上；
- 大块张量通过集合通信批量移动，而不是细粒度随机 load；
- 用张量并行、专家并行的分片规则减少跨 GPU 数据量；
- 对热点数据复制，对大容量冷数据分片；
- 将通信与 GEMM 重叠，隐藏而不是假装不存在传输时间。

因此，“统一寻址”是一种可编程能力，不是一张性能支票。

## 3. NVSwitch 非阻塞，究竟保证了什么

“非阻塞”常被误读为“任何工作负载都不会拥塞”。在这类系统里，它更准确的含义是：交换 fabric 的双分带宽与 GPU 端口总注入带宽匹配，在满足路由和流量分布条件时，不需要像过订阅网络一样主动牺牲某组端口。

但应用仍可能拥塞：

1. 多个源同时向同一目标 GPU 写入，目标端口成为热点；
2. MoE 路由不均，使少数专家接收远多于平均值的 token；
3. 小消息受固定延迟和软件调度主导，线速没有意义；
4. 多个 communicator 的 collectives 同时占用相同端口；
5. 归约操作的执行资源或内存读写先于链路饱和。

可用一个简化的通信时间模型看这件事：

```text
T_comm ≈ N_steps × α + bytes_on_critical_path / B_effective
```

- `α` 是每一步的固定软件、同步与链路延迟；
- `B_effective` 是协议和拓扑下的持续有效带宽，不是端口线速；
- 小消息由第一项主导，大消息由第二项主导。

机架级 NVLink 的价值，是同时降低 `α`、提高 `B_effective`，并扩大可以采用低跳数算法的 GPU 范围。

## 4. 为什么要从 8 卡扩成 72 卡

答案不是“模型有 72 份权重”这么简单，而是并行策略在跨越 8 卡边界时会付出网络税。

### 4.1 Tensor Parallel：每层都可能通信

以列并行/行并行 Transformer 为例，一次前向中通常会出现 AllGather 或 AllReduce/ReduceScatter。若 TP=8 恰好落在单机 NVSwitch 内，通信在 scale-up fabric 完成；若 TP=16 跨越两个 8 卡服务器，关键路径进入 HCA、交换网络和远端 HCA。

72-GPU domain 允许更大的 TP 或 context parallel group 留在 NVLink 内。但 TP 并非越大越好：每 GPU 的矩阵变窄后，GEMM 效率下降，collective 固定成本上升。最佳点仍需测量。

### 4.2 Expert Parallel：All-to-All 最怕热点和边界过早

MoE 的 dispatch/combine 本质是两次 token 重排。若每个 rank 在一次 dispatch 中发送 `M` 字节，理想均匀流量下每 rank 大约向其他 `p-1` 个 rank 发送：

```text
bytes_sent_per_rank ≈ M × (p - 1) / p
```

但实际 top-k 路由不是均匀随机数。某个专家的负载超过容量因子后，要么丢 token，要么排队，要么跨域搬移更多数据。低延迟、单跳的 72-GPU fabric 能降低搬移成本，却不能替代负载均衡损失、专家放置和 capacity factor 设计。

### 4.3 Pipeline/Data Parallel：仍然需要 scale-out

72 GPU 不是集群终点：

- 数据并行梯度同步经常跨机架；
- pipeline stage 之间可能跨机架发送激活；
- checkpoint、数据加载和服务入口走存储/前端网络；
- 超过 72 GPU 的训练必须把多个 NVL72 连接起来。

更准确的结论是：**NVL72 把高频、细粒度的模型并行尽可能留在 scale-up 域，把较容易批量化的数据并行放到 scale-out 域。**

## 5. 一台 NVL72 实际上有三张网络

参考架构明确分出三个 physical fabric：

| Fabric | 典型设备 | 主要流量 | 设计重点 |
|---|---|---|---|
| GPU compute E/W | 每 tray 4 个 ConnectX-8 HCA | 跨机架 RDMA、collectives | rail-optimized、无阻塞 leaf-spine |
| CPU converged N/S | Grace/BlueField uplink | 数据、存储、服务入口、管理业务 | 与训练后端隔离故障与拥塞 |
| OOB | BMC、交换机管理口 | PXE、监控、固件、救援 | 即使数据面故障仍可运维 |

每个 compute tray 有 4 个双端口 ConnectX-8。单个 HCA 以两个 400Gb/s 端口工作，合计 800Gb/s；72 张 HCA 对应整架 144 个 400G 计算网络端口。

rail-optimized 的思路是让同一 local GPU index 的 HCA 接到同一 rail，使分层 collective 先在机架内归约，再由对应 rail 跨机架传输，减少 spine 级流量混洗。

这不是布线偏好，而是并行策略的一部分。GPU↔HCA 的 NUMA 亲和性、rank mapping 与交换机 rail 必须一致；否则一个看似健康的作业会先绕过主机互联或跨 NUMA 域，再进入网卡。

参考：[NVL72 Logical Architecture](https://docs.nvidia.com/enterprise-reference-architectures/nvl72-ai-factory/latest/network-logical-architecture.html)和 [Networking Physical Topologies](https://docs.nvidia.com/enterprise-reference-architectures/nvl72-ai-factory/latest/networking-physical-topologies.html)。

## 6. 130 TB/s、800G 与 HBM 8 TB/s 不能直接横比

三类数字分别描述不同路径：

```text
本地 HBM:       GPU core ↔ own HBM          最高 8 TB/s/GPU
机架 scale-up:  GPU ↔ NVSwitch ↔ GPU        1.8 TB/s/GPU 双向聚合
跨架 scale-out: GPU ↔ HCA ↔ fabric ↔ HCA   与 HCA/rail 配置相关
```

以每 tray 4 个 HCA、每 HCA 800Gb/s 双端口合计为例：

```text
4 HCA × 800 Gb/s = 3,200 Gb/s = 400 GB/s/tray（端口线速合计）
400 GB/s ÷ 4 GPU = 100 GB/s/GPU（平均线速口径）
```

这只是按 GPU 平均分摊的端口带宽，不是单 GPU 一定能获得的端到端吞吐。协议头、FEC、PCIe/NVLink-C2C 路径、交换拥塞和 collective 算法都会继续减小有效值。

对照三个数量级，就能理解为何系统希望把高频 TP/EP 通信留在机架：本地 HBM、机架 NVLink、跨架 RDMA 之间并非同一数量级和延迟。

## 7. 142kW 是架构参数，不是机房附注

官方参考架构给出的整架最大功率约 142kW，并配置 8 个最高 33kW 的电源 shelf。不能把 `8 × 33 = 264kW` 直接当作 IT 负载；安装转换能力还要覆盖供电路径、冗余和瞬态设计，整架最大 IT 功率仍以系统说明的 142kW 为准。

若用 142kW 做容量推导：

```text
日耗电上限 = 142 kW × 24 h = 3,408 kWh/day
热负荷      = 142 kW ≈ 484,500 BTU/h
```

真实平均功率取决于 workload 和 power cap，但电气、CDU、冷板、歧管、漏液检测和应急策略必须按峰值与瞬态设计。对传统 10–20kW 风冷机架来说，这不是“多插几根电源线”能解决的问题。

整架设计还扩大了故障影响面：

- 单 GPU 故障可能只隔离一个 rank；
- compute tray 维护影响 4 GPU；
- NVSwitch、fabric manager 或背板问题可能影响整个 72-GPU domain；
- CDU/供电路径问题可能让整架退出服务。

所以可维护性指标应包括：降级拓扑是否受支持、作业能否缩容重启、tray 热插拔边界、备件到场时间，以及恢复后是否需要重建 fabric。

## 8. AMD Helios：相同的 72，另一套取舍

AMD Helios 也采用 72 张 GPU，但不是 NVL72 的简单等价物。当前公开设计使用 72 张 MI455X、EPYC Venice、Pensando Vulcano 网络设备，并用 UALink over Ethernet（UALoE）构建 scale-up。

MI455X 的公开规格包括 432GB HBM4、23.3TB/s HBM 带宽与 3.6TB/s 双向 scale-up 带宽。于是：

```text
72 × 432 GB = 31.104 TB HBM4
72 × 3.6 TB/s = 259.2 TB/s ≈ 260 TB/s scale-up 聚合
```

UALink 1.0 不是“普通以太网跑 RoCE”的另一个名字：

- 使用 Ethernet PHY，但定义面向加速器的 load/store/atomic 语义；
- 软件负责一致性，不宣称硬件 cache coherent；
- 200GT/s/lane，x4 station 每方向 800Gb/s；
- 面向 4m 内、1–4 个机架、最多约 1,024 endpoint；
- 固定 FLIT、credit flow control、link-level retry，并支持端到端鉴权/加密。

这条开放路线的潜在价值是让不同厂商共同实现 scale-up fabric；代价是生态需要同时验证 NIC/switch、firmware、runtime、collective library 与故障处理。规格开放不自动等于部署成熟。

来源：[AMD CDNA Architecture](https://www.amd.com/en/technologies/cdna.html)、[AMD Helios](https://www.amd.com/en/products/rackscale-solutions/helios.html)和 [UALink 1.0 White Paper](https://ualinkconsortium.org/wp-content/uploads/2025/04/UALink-1.0-White_Paper_v3.pdf)。

## 9. 用一个决策模型判断是否真的需要 72 GPU scale-up

先把 workload 的每层关键路径写成：

```text
T_layer ≈ max(T_compute, T_HBM, T_scale-up, T_scale-out)
          + exposed_sync_latency
```

再分别测量/估算：

- `T_compute`：同一 shape、精度和融合策略下的 GEMM/attention 时间；
- `T_HBM`：权重、KV、激活实际读写字节 ÷ 可持续带宽；
- `T_scale-up`：TP/EP/CP 每层消息量 ÷ collective 有效带宽；
- `T_scale-out`：跨架 DP/PP 通信及拥塞时间；
- `exposed_sync_latency`：无法与计算重叠的尾延迟。

72-GPU scale-up 在以下条件下最有价值：

1. 模型无法在 8 GPU 内形成高效 TP/EP group；
2. 每层存在高频 collective，小消息延迟不可隐藏；
3. MoE 的 dispatch/combine 占 step time 的显著比例；
4. 把并行组留在机架内能明显减少跨架流量；
5. 数据中心确实能承载整架功率、冷却与故障域。

反之，如果工作负载是小模型、高 batch 独立推理、松耦合数据并行或 GPU 经常空闲，72 卡机架的互联能力可能无法转化为经济收益。

## 10. 到货后怎样证明“72 卡是一个可用域”

验收不能停在设备枚举。至少分五层：

1. **物理层**：所有 NVLink lane、NVSwitch port、HCA port、温度和功耗状态正确；
2. **拓扑层**：GPU↔CPU↔HCA 亲和性与布线设计一致，rail 没有接反；
3. **内存 fabric 层**：Fabric Manager、NVLSM、IMEX 正常，跨 OS 域 P2P 读写与原子操作通过；
4. **collective 层**：按消息尺寸扫描 AllReduce、AllGather、ReduceScatter、All-to-All，记录延迟、`algbw` 和尾部离群；
5. **模型层**：用生产 shape 测 step time/token latency，并把 compute、HBM、scale-up、scale-out 暴露时间拆开。

还应做故障注入：禁用一条链路、一个 HCA 或一个 compute tray，确认告警、隔离、作业失败语义和恢复流程符合设计。一个只在全新、全健康状态跑得快的 72 卡系统，不算完成生产验收。

## 结语：机架已经成为计算机，但不是单体计算机

72-GPU 设计真正改变的是**高性能通信域的半径**。它让多节点 GPU 可以用 load/store 语义和单跳交换 fabric 协作，使更大的张量并行和专家并行组不必过早进入数据中心网络。

但节点、内存所有权、故障域和软件初始化仍然存在。理解这层张力，才能读懂 130TB/s、20.7TB HBM、800G 和 142kW 分别意味着什么，也才能判断工作负载究竟需要一台机架级计算机，还是只需要更多普通 GPU 服务器。
