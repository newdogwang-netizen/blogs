一份资源申请已经写入分配结果，Pod 也被绑定到了节点，但应用访问设备仍然失败。传统的排障思路容易停在“调度成功，所以设备应该可用了”。DRA 让我们更清楚地看到：**选中设备、记录归属、准备访问条件和成功执行，是四个不同的阶段。**

大会 [DRA 架构与 IMEX 分配分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1223308)讨论了超节点拓扑，以及如何通过调整状态对象的粒度减少更新冲突。以下依据议程摘要、Kubernetes 与 NVIDIA 官方资料分析；没有复现该案例的性能结果，也未逐一审计相关 PR。

## 一、“两张 GPU”没有描述设备之间的关系

假设工作负载需要两张相互可高效访问的 GPU，并希望它们与某个 NIC 有合适的 PCIe/NUMA 邻近关系。传统整数资源能表达数量，却很难仅凭一个计数表达设备型号、属性和关系。

DRA 通过结构化设备信息与请求，让分配决策不只面对一个整数。ResourceSlice 描述驱动发布的资源库存，DeviceClass 表达一类设备的选择规则，ResourceClaim 表达一次申请，Pod 使用 claim。不要把 ResourceSlice 的名字理解成 GPU 已经被物理切片：这里的 slice 首先是 API 中组织资源描述的对象。[DRA 概念文档](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/)

这里仍有一个前提：驱动必须发布有意义的属性，请求和调度侧也必须能消费它们。硬件拥有 NVLink、NIC 与 NUMA 关系，不意味着任意部署都会自动把这些关系准确编码进可分配模型。

## 二、从声明到可用，中间有一条准备路径

{% include infra-figure.html file="dra-request-lifecycle" alt="设备驱动发布库存，用户创建 claim，调度器分配并绑定，kubelet 请求节点驱动准备，容器最后获得设备访问条件" caption="图 1 · DRA 主路径简化图。库存、分配结果和节点实际准备状态由不同组件维护；图不表示一个跨组件原子事务。" %}

在结构化分配模型中，调度器把节点选择和设备分配结合起来考虑。分配结果进入 API 状态之后，节点上的 kubelet 还需要请求 DRA 驱动准备资源；驱动再把所需设备信息交给容器运行链路，例如通过 CDI 对接运行时。释放时也存在对应的清理过程。[Kubernetes v1.34 DRA 发布说明](https://kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/)

这条路径解释了为什么“已经分配”不应被当作最终 Ready。如果节点插件暂时不可达、设备配置失败或访问权限没有准备好，控制面仍可能保留分配结果，而应用还不能启动。反过来，如果实际准备已经完成但状态回复丢失，重试又必须避免重复创建不一致的资源。

因此，驱动的 prepare/unprepare 需要面对重试与幂等问题。幂等不是简单地“发现目录存在就返回成功”，而是确认已有配置属于同一申请、具有正确身份和版本，且足以满足本次准备目标。

## 三、拓扑约束不是一层标签就能全部表达

NUMA、PCIe、节点内 NVLink 与跨节点 fabric 处在不同尺度。节点标签适合描述较粗的归属；具体设备属性适合区分节点内可选择的对象；应用通信组又决定哪些设备必须相互协作。

一个有用的设计方法，是先把需求写成关系，而非立即写 YAML。例如：“这两个计算设备必须属于同一允许的互联域”“这个网络设备应与对应计算设备邻近”“同一作业成员需要一致的访问控制配置”。然后逐项判断由哪个 API、驱动或工作负载控制器负责。

如果一个约束只能在分配之后检查，就要明确检查失败是否会释放原分配并重新排队，否则它会变成长期占用但无法服务的资源。所谓 topology-aware，必须能说明拓扑在哪里产生、何时生效、失败后怎样收敛。

## 四、IMEX 管的是跨 OS 域的内存共享条件

IMEX 服务用于支持多节点 NVLink 环境中的 GPU 内存导入与导出协调。数据访问依赖已经存在的 NVLink fabric；IMEX 不会给原本通过以太网连接的服务器“创建 NVLink”。这对阅读超节点相关资料尤其重要：**18 台 HGX B300 的常规跨节点网络，不会因为安装 IMEX 就变成一个 NVL72 互联域。** [IMEX 官方概述](https://docs.nvidia.com/deploy/imex-service/overview.html)

IMEX channel 进一步参与访问隔离。需要共享的进程必须获得正确 channel 的访问条件，多节点上的分配要一致。官方还指出一个容易忽略的误配置：如果所有用户同时能访问公共 channel 0，即使另行分配了专用 channel，也可能破坏预期隔离；应按文档约束核实每个用户实际可访问的设备节点。[IMEX Channels](https://docs.nvidia.com/multi-node-nvlink-systems/imex-guide/imexchannels.html)

这类资源不能完全当作单节点私有设备处理。一台节点准备成功，而另一台节点使用了冲突或不一致的分配，整个作业仍可能失败。设备数量没有变，协调状态却已经成为关键依赖。NVIDIA 的 [DRA driver 项目](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu)是进一步追踪实际 API 与部署前置条件的入口；这些驱动扩展并不等同于 Kubernetes 核心 API。

## 五、为什么状态对象的粒度会影响规模

大会摘要描述了三段演进：多个参与者更新共享状态时产生冲突；随后集中更新；再把分布式更新组织到与拓扑对齐的状态对象上。下面用一个简化场景解释这一思路，不把示意对象当作原项目逐字对应的 CRD。[对应场次](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1223308)

设节点 A、B 同时读取状态版本 7。A 写入自己的准备结果，状态变为 8；B 仍按版本 7 更新，就需要处理冲突、重新读取并再次提交。即使两者实际修改的是不同设备，若写入方式与对象粒度让它们竞争同一个版本，仍会相互干扰。

{% include infra-figure.html file="dra-state-sharding" alt="并发写共享对象引发版本冲突；集中写串行化；按拓扑分区的对象缩小不相关更新之间的竞争" caption="图 2 · 三种状态组织的分析示意。分片减少无关写入竞争，不会自动消除同一分片内的并发或跨分片协调。" %}

集中式写入让更新顺序更容易控制，却可能把队列、协调者和故障恢复变成瓶颈。按拓扑分片的价值在于，让必须一致处理的成员靠近同一协调边界，同时避免不相关拓扑域互相争用。

但分片不是越细越好。若一个作业跨越多个分片，分配会重新遇到部分成功：A 分片已经保留资源，B 分片失败。设计必须回答保留如何超时、如何撤销、谁负责最终完成，以及协调者重启后如何识别已有进度。否则减少了 API 冲突，却制造了资源泄漏。

## 六、健康状态与释放不能只靠删除记录

一个设备从健康变为不健康，对新申请和正在运行的申请是两个问题。对新申请，可以避免继续选择；对已有作业，需要决定是否通知、重启、迁移或由应用处理。状态上报只是信息，处置策略仍有独立责任。

释放也一样。API 对象已经消失，不证明节点权限、挂载、channel 或其他准备结果已经撤销。如果节点不可达，应保留足以恢复清理的信息，而不是因为删除成功就立刻把同一资源交给另一个租户。

落地时还应保留版本表：Kubernetes 核心 DRA API、每项 feature gate、驱动版本、GPU/驱动支持，以及所用调度器。历史上的核心 DRA GA 说明，不等于设备健康、共享容量、特定拓扑扩展也在所有版本中具有相同成熟度。本文采用上述 1.34 发布说明解释核心路径；大会涉及的 1.36 能力与具体驱动扩展需按部署版本单独核对。

## 七、怎样检验架构是否真的改善了分配

只测“创建到 Running”会把镜像拉取和设备准备混在一起。建议分别记录 claim 等待、分配提交、节点 prepare、应用首次设备访问成功的时间，并观察各阶段 P50/P95/P99。

状态设计则看每次成功分配对应的 API 写入量、冲突重试次数、队列长度与资源残留。压测时不仅增加设备数量，还要增加同时申请和同时释放的数量；库存很大但更新稀疏，并不能检验并发热点。

最后注入三类故障：准备完成后丢失响应、协调者更新一半后重启、部分节点在释放时不可达。每次都要核对 API 中的归属与节点上的实际权限，直到二者重新一致。若只能看到 claim 已分配、Pod 已运行，却查不到 prepare 和 unprepare 的进度，这套系统还缺一段必要的排障信息。
