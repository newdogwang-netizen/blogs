训练进行到一次梯度归约时，一个 rank 退出了。其余 GPU 仍然有参数、仍然可以计算，却等待一个永远不会到达的参与者。把 communicator 重新建起来，是否就能继续下一步？

还不能。某些 rank 可能已经更新了参数，另一些停在更新之前；失败 rank 上还可能存着不可缺少的参数或优化器分片。通信层回答“现在谁能一起通信”，训练层还要回答“这些参与者应该从哪个一致状态继续”。

大会的 [Meta 训练容错分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1223450)把 TorchComms、成员重配置与 peer memory/local disk checkpoint 放在同一条恢复链路里。下面根据公开摘要和官方接口分析各阶段的职责；没有部署 torchstore，也未做故障注入实测。

## 一、故障传播范围由依赖图决定

一个 rank 可能同时属于数据并行、张量并行或流水线中的多个通信关系。进程失效先影响当前操作，随后通过依赖传播：某个梯度没完成归约，优化器不能更新；某个流水阶段没输出，下游也无法推进。

因此，“只坏了一张卡”不说明只损失一张卡的工作量。恢复边界应结合并行策略决定。数据并行副本之间可能有冗余模型状态；张量并行组内的不同 rank 则通常持有同一次计算必需的不同部分。缺少其中一份，剩余成员并不自然组成一个更小但等价的模型。

慢节点、网络中断和程序死锁还可能呈现相似的等待现象。检测器看到的是超时或错误证据，不应把每次延迟都直接解释成设备永久损坏。超时过短会误杀健康作业，过长则扩大空转损失。

## 二、communicator 重配置解决哪一层

NCCL 的 `ncclCommShrink` 可以从已有 communicator 排除指定 rank，创建新的通信组；参与调用的是保留在新组中的成员，新的 rank 编号也会重排。错误恢复还涉及对父 communicator 未完成操作的处理模式。[NCCL communicator 文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/communicators.html)

这些接口很重要，但它们没有自动重分片模型、修改全局 batch，或重建优化器状态。revoke、shrink、grow 等机制应按具体 NCCL/通信后端版本理解，不能仅看同名 API 就假设异常路径和可组合性完全相同。

[TorchComms 的官方介绍](https://pytorch.org/blog/torchcomms/)与后续 [Python-first 通信开发记录](https://docs.pytorch.org/devlogs/distributed/2026-05-14-python-first-comms/)展示了更灵活的通信接口方向。项目在不同时间使用的后端名称和成熟度会变化；本文讨论责任分层，不给出一个混合不同年代接口的“通用恢复脚本”。

## 三、训练状态必须对应同一个提交边界

{% include infra-figure.html file="training-recovery-layers" alt="故障后先停止旧轮次与重建通信成员，再选择一致 checkpoint、恢复状态和数据位置，最后开始新训练轮次" caption="图 1 · 双层恢复示意。通信恢复是必要阶段，不是训练正确性的最终证明；具体阶段可重叠，但依赖不能跳过。" %}

一个可恢复点通常需要参数、优化器状态、训练步数、学习率调度状态、随机数状态，以及数据采样或消费位置。不同训练方案还可能有梯度累积、混合精度 scaler 和应用专用状态。[PyTorch Distributed Checkpoint 文档](https://docs.pytorch.org/docs/stable/distributed.checkpoint.html)

关键不是“把这些东西都存过一次”，而是它们描述同一个逻辑时刻。例如参数来自 step 100，优化器动量来自 step 99，数据位置却已经前进到 step 101，这不是一个一致 checkpoint。程序可能继续输出 loss，但轨迹已经改变。

异步 checkpoint 又增加一个边界：后台写盘时，前台是否仍在修改同一块内存？需要先获得稳定快照或受控的 staging 副本，再让异步 I/O 读取它。把写入丢到后台线程，并不自动减少前台需要承担的一致性工作。

还要区分数据已经写入某处与 checkpoint 已提交可用。若只完成部分分片，恢复程序应拒绝这份不完整状态，并回到已确认的上一版本。提交记录、校验与分片清单在这里不是附属元数据，而是恢复协议的一部分。

## 四、为什么不只写共享文件系统

共享存储提供了较清晰的持久化入口，但在大模型、高频 checkpoint 下，数据聚合与写入可能昂贵。大会摘要讨论了 peer memory 与 local disk 等路径，并以 torchstore 为例说明 RDMA 传输用于快速恢复的方向。[对应分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1223450)

{% include infra-figure.html file="checkpoint-failure-domains" alt="检查点可保存在对端内存、本地磁盘和持久共享存储；越快的近端层通常需要另行验证相关故障下的存活能力" caption="图 2 · 分层 checkpoint 的设计比较，不代表某个项目默认采用三层。副本位置需要跨越所要容忍的故障域。" %}

对端内存能够减少某些持久存储路径的等待，却需要对端仍然存活；本地磁盘可以熬过进程退出，却未必能熬过整机丢失；共享存储也有自身故障和吞吐边界。速度、耐久性和可访问性是不同维度。

一个典型误区是把两个副本放在同一台主机，便称作容忍单节点故障。另一个更隐蔽的误区，是副本分属两台主机，却仍依赖同一个会同时失效的电源、机架或控制服务。副本数必须和故障域一起讨论。

合理的分层方案可能用近端 checkpoint 处理常见单进程故障，周期性把更少的版本提升到更耐久的层。失效范围扩大时允许退回更旧但存活的状态。这种设计需要明确可接受的回退量，而不是用一个“秒级恢复”覆盖所有失败情形。

## 五、恢复是一轮有版本的协议

恢复期间最危险的情况之一，是部分成员开始新一轮训练，而另一些还在完成旧轮次的写入或提交。一个清晰的设计需要恢复 epoch 或等价标识，让旧轮次的迟到结果不能覆盖新状态。

在机制上可以这样推导：先冻结新的训练进展并终止或隔离失效通信；协调新的成员集合；选定共同认可的 checkpoint；恢复参数和其他状态；恢复数据消费位置；最后让新成员以新的轮次进入训练。具体框架可以优化和重叠这些阶段，但必须维持同样的语义边界。

world size 改变时，还要检查有效 batch、归约除数、学习率与数据分片。数据并行少一个副本，可能可以通过重新定义这些量继续；张量并行少一个成员，则往往需要重新分片与加载。communicator 变小不等于任意并行维度都支持在线缩容。

## 六、用有效训练时间评价恢复

可以用一个简化模型理解 checkpoint 间隔的权衡。设保存开销为 C 秒，间隔为 τ 秒，作业平均故障间隔为 M 秒，恢复耗时为 R 秒。在故障稀疏、发生时刻相对均匀、τ 远小于 M 等假设下，损失比例近似为：

```text
损失比例 ≈ C / τ + (τ / 2 + R) / M
```

第一项是平时保存成本，第二项是故障后的平均回退与恢复成本。只最小化这两个有关 τ 的项，可得到 `τ ≈ √(2CM)`。这是教学模型，不是生产参数推荐；异步保存、相关故障、不同层级 checkpoint 和可变吞吐都会改变假设。

代入一组假设值：C=20 秒、M=36000 秒，得到 τ≈1200 秒，即约 20 分钟。这里的十小时故障间隔没有硬件统计依据；实际配置应代入作业的观测数据，并检查前面的模型假设是否成立。

## 七、先验证恢复正确，再验证恢复速度

测试顺序可以从 step 边界的单进程退出，扩展到 collective 进行中的故障、保存中断，再到整节点与相关节点丢失。每次都记录恢复采用的 checkpoint、成员变化、重复或跳过的数据范围，以及恢复后参数/优化器是否一致。

可确定性复现的配置可以做严格对照；包含非确定性 kernel 的训练则需要数值容差或统计比较，不能强行要求所有情形逐位相同。另一方面，只看到 loss 最终下降也不足以证明数据没有重复或丢失。

记录恢复耗时时，终点可以设为恢复后第一个完成一致性检查的训练 step，并另外记录回退了多少有效工作。这样既能看到通信重建节省的时间，也不会漏掉重新加载状态和重算数据的成本。
