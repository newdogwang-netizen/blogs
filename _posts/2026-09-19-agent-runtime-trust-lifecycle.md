一个 Agent 下载用户提供的项目，安装依赖，运行测试，再把结果提交到远端。平台为它启动了独立容器，但如果项目里的构建脚本读取了环境变量中的访问令牌，它能用这个令牌做什么？

容器即使没有被突破，越权也可能已经发生。Agent 的风险同时来自可执行内容、工具调用和被委托的身份。把这三件事混成“沙箱安全”，往往会得到一个执行边界很强、业务权限却过大的系统。

本文以大会的 [Agent Runtime 与 Open Infrastructure 分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1309274)为入口，结合 [Agent Sandbox](https://agent-sandbox.sigs.k8s.io/docs/) 与 [Kata 的集成说明](https://katacontainers.io/blog/kata-containers-agent-sandbox-integration/)展开。下面的权限网关和验收方法是本文的架构分析，不表示这些项目自动实现了全部安全能力；也不把网页文档中的休眠能力等同于所有后端均可保存完整内存状态。

## 一、先画三条边界

第一条是执行边界：不可信代码能够访问哪些系统调用、文件、设备与内核接口。第二条是网络边界：它能向哪些目的地发送数据，是否能访问元数据服务、控制面或其他租户。第三条是身份边界：它持有的凭证能代表谁，对哪些资源做哪些操作。

{% include infra-figure.html file="agent-trust-boundaries" alt="用户授权通过任务控制器和工具网关进入外部服务；沙箱执行代码，与模型服务、凭证服务分别隔离" caption="图 1 · 建议的信任边界示意。沙箱负责限制执行环境，工具网关负责约束动作；两者不能互相替代。" %}

Kata 通过轻量虚拟机提供与普通共享宿主内核容器不同的隔离边界，但 VM 不能替你判断“这次工具调用是否获得用户授权”。同样，严格的工具网关也不能替代执行环境隔离：恶意依赖仍可能攻击所在运行环境。

平台选型前要先确定执行什么代码。自有代码的批处理、第三方插件执行和面向公众的任意代码环境，对隔离、出网与凭证管理的要求并不相同；同一个 runtime 也可能需要完全不同的部署配置。

## 二、任务申请的应当是环境契约

Agent Sandbox 用 Sandbox 表达有稳定身份的隔离工作负载，并通过模板、claim 与 warm pool 等对象组织创建和分配。它将环境生命周期从业务代码里提取出来；实际隔离程度仍取决于选用的运行时和部署配置。[项目概览](https://agent-sandbox.sigs.k8s.io/docs/)

对平台而言，模板不是一段便于复用的 YAML 而已。它应表达可审计的环境契约：基础镜像 digest、运行时类别、CPU/内存与磁盘限制、网络策略、允许挂载的数据、最长寿命，以及状态清理方式。若模板可以被普通任务随意加入宿主目录或高权限选项，“从模板申请”就不再是一个有意义的安全边界。

一次任务至少经过申请、环境分配、身份绑定、执行和回收五个阶段。预热环境可以提前完成镜像拉取和启动，却不应提前装入某个用户的长期令牌。身份绑定应尽量靠近实际任务执行，并能在取消时撤销。

## 三、工具授权不能只在入口检查一次

设用户只允许 Agent 读取仓库 A，并在临时分支上提交修改。若运行环境里放的是能管理整个组织的令牌，即使最初的提示词写得很严格，实际授权边界仍然过大。

更稳妥的架构是让任务获得短期、限域的身份，或通过校验任务上下文的工具代理执行敏感动作。网关检查的应是结构化对象——任务身份、目标资源、动作、有效期——而不是依赖模型生成的自然语言说明。执行日志还要关联到授权记录，使“哪个任务、依据哪次授权、对哪个对象做了什么”可以追溯。

这是一种纵深设计，不是对 prompt injection 的绝对免疫声明。被授权读取的数据仍可能被错误处理；允许的写操作也可能内容不正确。高影响动作还需要业务校验、幂等键或人工确认，具体由风险等级决定。

## 四、任务与沙箱有两套生命周期

任务结束不一定意味着沙箱立即销毁：用户可能希望稍后继续修改文件。沙箱仍在运行也不意味着任务仍然有权调用外部服务：任务可能已被取消或授权已过期。

必须分别回答三种“恢复”：PVC 还在，意味着文件可能保留；进程重新启动，意味着程序可能恢复服务；内存快照可恢复，才可能保留更完整的执行上下文。它们的实现条件、兼容边界和风险都不同。连接重建、外部 API 的副作用、已过期的令牌，更不会因为恢复了一份磁盘而自动恢复正确。

平台可以把可恢复任务设计成显式检查点：保存工作目录与任务进度，重新创建环境，再用新身份续作。这样不一定拥有最低的恢复延迟，却更容易解释故障后的授权与幂等语义。是否采用内存级快照，应单独评估运行时、存储、内核/设备兼容和快照敏感信息，而不是把它写成沙箱的天然属性。

## 五、预热池用持续成本换等待时间

冷启动时间通常包含排队、调度、镜像获取、运行时启动、应用初始化和身份准备。warm pool 只能提前支付其中一部分；如果真正瓶颈是外部包下载或凭证服务，预热十倍 Pod 也未必解决问题。Kata 集成文章明确提到了预热能力，但没有给出适用于所有环境的启动延迟保证。[Kata 官方说明](https://katacontainers.io/blog/kata-containers-agent-sandbox-integration/)

一个可用于容量估算的起点是 Little 定律：稳态平均占用量约为到达率乘以平均服务时间。但预热池面对的是尾部突发，因此还要看突发窗口内的并发到达，而不是只用全天平均 QPS。

例如，假设平均每秒 2 个任务、环境平均占用 30 秒，平均活跃环境约为 60 个；这不意味着维持 60 个空闲预热环境才合理。活跃池和空闲预热池是两个数量，后者需要结合冷启动预算、突发大小和补池速度确定。这是算例，不是项目实测。

复用还有安全成本。一个环境从租户 A 转给租户 B 前，必须确保文件、进程、缓存、凭证和网络状态不会残留。对于难以证明清理完整的环境，销毁重建通常比原地“清空一下”更容易审计。预热应优先复用未分配的干净环境，而不是无限复用执行过未知代码的实例。

## 六、取消、重试与回收时要检查什么

建议在隔离测试环境中检查以下情况，所有动作都限定在测试租户与测试凭证中：

| 场景 | 需要证明的边界 |
| --- | --- |
| 用户取消任务，但进程仍存活 | 凭证和工具调用权是否失效，何时终止计算 |
| 工具响应超时，Agent 重试 | 写操作是否有幂等约束，能否区分未执行与已执行未确认 |
| 沙箱节点重启 | 文件、进程、任务进度分别恢复到哪里 |
| 任务耗尽磁盘或创建大量子进程 | 是否影响同节点或同租户之外的工作负载 |
| 模板升级与 warm pool 共存 | 新任务是否仍可能分到旧环境，如何逐步淘汰 |
| 多租户连续分配 | 能否发现前一任务的数据或身份残留 |

最终的可观测对象也应该围绕任务，而不只围绕 Pod：申请等待、绑定耗时、执行时间、取消生效时间、回收完成时间，以及工具调用的授权拒绝原因。否则平台可能同时显示“Pod 全部健康”和“用户的任务无法安全结束”。

如果只能先做一项测试，可以从“取消任务后，进程还活着”开始：外部调用是否立即被拒绝，已发出的写操作怎样确认，环境里留下的文件归谁。这个场景会同时经过运行时、权限服务和任务控制器，最容易暴露三者之间遗漏的交接。
