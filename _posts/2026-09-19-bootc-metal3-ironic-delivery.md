同一组 GPU 节点使用相同型号，重装后却出现不同的内核、驱动或网络配置。问题未必来自装机工具不够自动化，而可能是系统版本从来没有被当作一个明确、可验证的制品管理。

大会的 [bootc、Metal3 与 Ironic 裸金属交付分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1223326)讨论了直接从 bootc 容器镜像交付主机的方向。以下结合摘要与项目文档说明安装和升级路径，不复述尚未核对完整细节的三种方案对比。安装涉及覆盖磁盘，文中只分析流程，不提供可直接执行的装机命令。

## 一、镜像格式背后，是发布边界的问题

传统磁盘镜像把一个已经布置好的磁盘内容作为交付物，适合已有成熟流程的环境。困难往往不在 qcow2 本身，而在构建系统、变更审计、镜像分发和主机升级各自形成了一条链路。

bootc 尝试把可启动操作系统纳入 OCI 制品体系，使团队能沿用熟悉的容器构建和注册表分发基础设施。镜像中包含启动系统所需的内核和用户态；主机启动后，基础用户态并不是默认套在一个普通应用容器里运行。[bootc 官方介绍](https://bootc.dev/bootc/)

这一区分很关键。OCI 是内容组织与传输格式，不是主机运行时隔离方式。把 OS 打包为 OCI，也不会自动把固件、磁盘中的业务数据和所有主机配置都变成不可变镜像的一部分。

## 二、谁声明主机，谁操作物理世界

在 Metal3 体系中，BareMetalHost 等 Kubernetes 对象表达期望状态，Bare Metal Operator（BMO）协调主机生命周期，Ironic 负责具体裸金属操作，并通过相应驱动与 BMC 等硬件管理接口协作。[Metal3](https://metal3.io/)、[Ironic 在 Metal3 中的职责](https://book.metal3.io/ironic/introduction.html)

Ironic 有自己的任务状态与持久化信息，BMO 又持有 Kubernetes 侧的期望状态。两者的协作不是一次 API 调用就能原子完成：重启、引导、部署和回报可能持续较长时间，中途任何组件都可能失联。

因此，控制器重试不能简单等于“再重装一次”。它必须先确认物理任务正在执行、已经完成，还是确实失败。否则控制面为了达到期望状态，反而可能反复触发破坏性动作。

## 三、制品到主机，仍然需要安装路径

直接消费 bootc 镜像，减少的是预先构建和分发某些磁盘镜像的需求，不是取消写盘、配置引导和首次启动。Ironic Python Agent 的公开接口包含通过 bootc 安装容器系统的操作；实际使用还要核对 Ironic、agent、Metal3、镜像与目标硬件的支持组合。[Ironic Python Agent 源码文档](https://docs.openstack.org/ironic-python-agent/latest/_modules/ironic_python_agent/hardware.html)

沿一台测试主机看，至少仍有这些问题：BMC 身份能否验证，目标启动路径是否可达，安装环境能否访问注册表，选中的目标磁盘是否正确，镜像架构是否匹配，首次启动配置能否成功，以及启动后能否回报状态。

其中最需要显式门禁的是磁盘选择与清理。不能因为 YAML 声明了某个镜像，就掩盖安装会覆盖数据的事实。设备序号可能随固件、插卡或启动环境变化，生产流程应使用已确认的稳定标识与硬件清单，并保留审批和回退条件。

## 四、镜像 digest 是起点，不是全部版本

一个 tag 可以移动，同一个名字在两个时间点可能指向不同内容。因此，交付记录应包含不可变内容标识，而不只是 `stable` 或 `latest`。但锁定镜像 digest，也不代表已经锁定整台 GPU 节点的行为。

对 GPU 集群，可以把验收单元设计为：系统镜像、内核、GPU/NIC 驱动、固件、容器运行时、设备插件，以及适用的硬件型号。这是本文的场景延伸，不是 bootc 自动生成的兼容矩阵。

同一个 OS 制品可以是多个验收组合的基础；组合是否可用，需要实际检查设备识别、网络路径和代表性工作负载。Linux 成功启动，只证明通过了比 AI 节点可用更早的一道门。

## 五、升级与回滚改变什么，不改变什么

bootc 的更新流程可以从注册表获取新版本并准备下一次启动所用的系统部署。其升级/回滚机制允许回到前一启动项，但持久状态有自己的规则，例如 `/etc` 与 `/var` 不能简单理解为每次随系统镜像完全重置。[升级与回滚文档](https://bootc.dev/bootc/upgrades.html)

这意味着系统回滚不等于业务数据回滚。新版本程序如果已经修改持久数据格式，旧系统镜像可能无法读取；新内核启动失败可以尝试回到旧启动项，但已经执行的固件更新也不会因此自动撤销。

发布流程必须分开记录“制品版本”“实际启动版本”和“业务数据兼容范围”。如果只看注册表里的 tag，会不知道主机是否已经重启；如果只看机器可 SSH，又会错过驱动和设备自检失败。

## 六、长时操作失败时，先识别阶段

| 故障位置 | 首先确认什么 | 不宜直接做什么 |
| --- | --- | --- |
| BMC 不可达 | 管理网络、身份与电源状态 | 反复修改主机期望状态触发新任务 |
| 安装环境访问注册表失败 | 证书、凭证、路由与制品是否存在 | 关闭验证后直接向全量推广 |
| 写盘中断 | 磁盘内容与部署任务是否仍在继续 | 把主机当作可用节点加入集群 |
| 安装完成但无法启动 | 启动项、磁盘布局、内核/固件组合 | 把“镜像下载成功”当作安装成功 |
| 启动成功但 GPU 自检失败 | 驱动/固件与硬件组合 | 让调度器先使用再观察 |

这些阶段应留在主机事件记录中。值班人员需要知道磁盘是否已写入、下次重试会从哪里继续，以及当前是否允许重新安装；只报一个“部署失败”不足以决定下一步操作。

## 七、把主机也纳入发布工程

可落地的最小流程是：构建带内容标识的 OS 制品；在可覆盖的测试服务器验证安装；保存硬件与软件组合；通过设备和业务自检；小批次替换或升级；观察完成后扩大范围。每一步都应留下实际结果，而不只是期望配置。

先用一台允许重装的测试机走完安装、升级和回滚，保存每次实际启动的版本、设备自检结果及残留的持久数据。确认这些记录足以解释失败后，再扩大批次。注册表里有了 OS 镜像，还只是这条交付链路的开始。
