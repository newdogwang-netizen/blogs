训练需要一个完整 GPU 组才有进展，推理需要稳定的请求延迟，Agent 又可能需要保存会话与工具执行环境。三者可以共享资源池，但很难用同一种生命周期策略管理。

大会的 [Volcano 维护者分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1222060)把跨集群训练、Kthena 推理服务层和 AgentCube 运行时放在一起讨论。本文把它看成一组明确分工的控制系统，而非一个项目自动包办所有能力。Kthena 的架构基线参考 **v1.0.0**；议程里标为 upcoming 的伸缩、session affinity、token-cost-aware 等方向不作为已验证生产能力。

## 一、三类工作负载的成功标准不同

训练作业的进展是有效 step 和最终结果；推理服务的进展是持续完成满足 SLO 的请求；Agent 会话的进展可能是带状态的任务，以及对外部系统已经发生的操作。

这决定了它们的中断成本。训练可以在检查点处暂停，却可能损失一段计算；推理副本缩容需要处理在途请求与缓存；Agent 环境退出可能丢失文件、进程或授权上下文。把三者都翻译为“删除一个 Pod”，只是忽略了应用语义。

因此，统一平台首先应统一身份、配额、优先级、资源库存与审计；如何开始、排空、恢复和终止，仍应由理解工作负载语义的控制器负责。

## 二、调度层负责位置与资源条件

Volcano 的调度层面向批处理与复杂工作负载提供队列、组调度等机制。它可以帮助决定资源何时、以什么条件分配给一个组，但不替推理路由器选择某个请求，也不替 Agent 判断某次工具调用是否授权。[Volcano 项目](https://github.com/volcano-sh/volcano)

这和第一篇 LWS 的讨论相接：工作负载对象表达哪些 Pod 属于同一个副本，scheduler 处理组资源和放置条件。多加一层对象时，需要说明它具体管理哪些字段、调用哪个下层接口，以及失败由谁处理。

## 三、Kthena 为什么拆成 controller 与 router

Kthena v1.0.0 的项目架构区分 controller-manager 与 router：前者协调模型工作负载生命周期，后者处理请求分类、后端选择与流量策略。其 README 也明确 router 是持续演进的参考实现，可以放在标准 API gateway 后面。[v1.0.0 README](https://github.com/volcano-sh/kthena/blob/v1.0.0/README.md)

这不是简单的代码模块拆分，而是时间尺度不同。模型副本的创建和加载可能很慢；单个请求的路由却需要快速作决定。路由器必须使用已经可用的容量，不能因为控制器刚刚发出了扩容意图，就把新容量当作存在。

PD 分离还要求路由器理解角色与请求状态。P 和 D 各自 Running，不足以证明它们兼容、能传输 KV，并且拥有合适的配对容量。生命周期控制面提供候选集合，数据面仍需维持请求级正确性。

这也说明为什么“prefix-cache-aware”不能只用一个标签实现。路由器看到的缓存与负载信息会过期；偏向缓存命中可能增加某个副本排队。最终需要比较节省的 prefill 与新增等待，而不是永远追逐最高命中概率。

## 四、AgentCube 接入的是另一种状态单元

大会摘要把 AgentCube 与会话路由、warm pool、隔离执行及 SDK 联系起来；这些是会场展示与项目方向的线索，不是本文已经验证的部署矩阵。[相关大会议程](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/)

Agent 会话与推理副本不能等同。一个会话可能调用共享模型服务，却拥有独立的代码执行环境；也可能因为用户暂停而长期闲置。扩大推理副本数，不会自动扩大可用沙箱数量；回收沙箱，也不应该误删会话需要保留的业务状态。

因此，公共资源层可以对 Agent 环境设定配额和优先级，具体会话分配、身份绑定、取消与清理仍需运行时层管理。其安全边界可结合第三篇的执行、网络和身份三条边界单独验收。

## 五、同一个字段最好只有一个最终写入者

当业务伸缩器、通用 HPA、模型控制器和人工运维都能修改副本数，系统会出现看似随机的回弹：A 想扩到 8，B 根据旧负载缩到 4，C 又按声明恢复到 6。每个控制器局部正确，组合却没有稳定含义。

一个便于评审的所有权表如下，具体项目应按自己的对象与集成方式填写：

| 决策 | 最终所有者应理解什么 | 其他层应提供什么 |
| --- | --- | --- |
| 可用总预算/配额 | 租户政策、资源成本、优先级 | 工作负载需求与使用事实 |
| 目标副本数 | SLO、加载时间、实际服务容量 | 指标、建议或伸缩入口 |
| Pod/设备放置 | 本地资源、组条件与拓扑 | 合法需求，不反复改写已分配结果 |
| 请求路由 | 就绪版本、负载、缓存和请求状态 | 可发现后端与能力信息 |
| 会话/作业回收 | 在途工作、状态保存与授权 | 回收期限、原因和容量压力 |

这里“一个写入者”指最终决策权，不妨碍多个组件提出建议。关键是建议有稳定入口，最终目标不会被多个循环各自覆盖。

## 六、统一平台的收益要减去集成成本

统一会增加新的依赖：CRD 版本匹配、controller 升级顺序、指标口径、错误传播与权限边界。如果一个组件升级改变了 Ready 的含义，上层路由和伸缩可能一起受影响。平台发布应验证组合，而非只验证每个 Helm chart 能安装。

最有价值的联合测试是一条完整负载变化：在线需求上升，平台请求容量，离线训练保存状态并释放，推理副本加载并预热，路由逐步使用新容量；随后需求回落，副本排空，资源再交给训练。在每个转折点注入失败，查看容量与状态是否会被重复承诺或过早回收。

接入这些组件前，可以先把上面的所有权表落实到实际对象和字段：谁写副本数，谁确认容量可用，谁批准回收，失败后由谁重试。若同一个字段仍有两个控制器持续覆盖对方，就应先解决这项冲突，再联调完整的扩缩容流程。
