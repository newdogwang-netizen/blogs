把模型里的 `.cuda()` 换成另一个设备接口，前向计算通过了，迁移是否完成？如果只考察一组固定输入，也许可以宣布一个演示成功。但把它放进生产，很快就会出现不同的问题：长序列触发一个未支持的算子，动态图反复重编译，多卡训练在 collective 上等待，升级框架后原来稳定的图又退回 eager。

多种加速器怎样接入同一套软件，是大会 [PyTorch 官方复盘](https://pytorch.org/blog/pytorch-conference-china-2026-advancing-the-open-source-ai-stack/)和 [FlagOS 教程](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1224095)涉及的话题。这篇从 PyTorch 的公开扩展接口出发，拆开“兼容 PyTorch”这句话：设备接入、图编译和多卡执行各自需要实现什么。没有跨芯片实测，文中不作性能排名。

## 一、从一次迁移失败往下追

设一个服务的矩阵乘法已经有高效实现，但 attention 前后的小算子仍走 CPU fallback。单独测矩阵乘，结果很好；测完整请求，却发现设备频繁同步，延迟远高于预期。

原因是算子性能不能直接相加为模型性能。一旦数据跨越设备边界，除了复制字节，还可能需要等待前序异步执行完成、改变布局，并等待主机再提交后续工作。图里一个“不重要”的算子，可能成为打断整条流水线的屏障。

因此，迁移时首先应收集执行路径，而不只是算子支持率。一个模型用了 100 种算子、支持了 99 种，并不能说明它已经达到 99% 的可用性；最后一种算子若位于每个 token 的关键路径，影响会被反复放大。

## 二、设备接口统一了入口，没有消除设备语义

PyTorch 为树外设备提供扩展路径。PrivateUse1 的意义，是让后端能接入已有分发机制，不必为了一个新设备把全部改动长期放在自己的框架分支里。但一个 dispatch key 不会自动提供分配器、随机数、stream/event、设备切换和序列化支持。[PyTorch PrivateUse1 接入教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)

这些接口听起来偏底层，却直接影响应用正确性。以 stream 为例：框架可能假定一项复制与随后的计算之间存在特定顺序；若后端仅把接口名称映射过去，却没有保留异步依赖语义，短测试未必暴露错误，负载上来后才可能读到尚未完成的数据。

另一类问题是设备与内存身份。一个 tensor 的逻辑形状相同，不代表 storage、stride、对齐要求和生命周期相同。后端需要回答：视图是否共享原存储？异步 kernel 尚未结束时，内存能否归还分配器？这些约束比“能创建一个 tensor”更接近可用后端的核心。

## 三、eager 可用与图编译可用，是两条验证路径

在 eager 路径里，算子逐个通过分发系统进入后端。图编译则需要先捕获可处理的计算图，再做分解、布局选择、融合与代码生成。PyTorch 的自定义 backend 接收 FX GraphModule 与示例输入，并返回一个保持原图调用契约的可执行对象；这不是简单地接管一个算子的函数指针。[Custom Backends 文档](https://docs.pytorch.org/docs/2.8/torch.compiler_custom_backends.html)

这里有三个常见断点。第一是 graph break：某段 Python 行为无法进入当前捕获区域，执行会被切成多个部分。第二是重编译：输入形状或 guard 条件变化，触发新图与新代码。第三是 lowering 缺口：捕获得到的图合法，但目标后端不能实现其中某种操作组合。

这三类问题不能都归到“算子不支持”。对应的修复方向分别可能是调整表达方式、改善动态形状策略，或者补充后端 lowering 规则。训练还多了一层：前向能编译不代表反向同样成立，自动微分保存的中间量也会改变内存压力。

一个实用的诊断顺序是：先看端到端 trace 中是否有设备往返，再看图被切了多少段，随后看重编译次数，最后定位热点 kernel。直接从峰值算力开始优化，容易解决一个不在关键路径上的问题。

## 四、多卡执行会暴露另一套兼容面

单卡正确之后，多卡并不是重复启动八次同一程序。分布式训练会依赖 process group、collective、异步 work handle、通信与计算 stream 的同步，以及故障后的行为。PyTorch 允许扩展通信 backend，但接口能注册只是起点。[分布式扩展文档](https://docs.pytorch.org/docs/stable/distributed.html#third-party-backends)

例如框架希望在梯度 bucket 就绪后启动通信，再与后续反向计算重叠。后端若把异步调用实现为阻塞等待，结果可能仍然正确，却失去重叠收益。反过来，若过早报告完成，优化器就可能读到尚未归约完的梯度。两种实现都可能通过“最终能输出 loss”的粗糙验收。

必须把通信拓扑也纳入测试。同一台机器内的互联、跨节点 NIC 路径、不同 rank 映射，对后端提出的约束并不相同。一个八卡节点的好成绩不能推出跨八个节点的相同比例；后者改变了数据路径、拥塞与同步成本。

## 五、验证矩阵比“支持哪些模型”更有解释力

下面这张矩阵是建议的验收结构，不是任何厂商的测试结果：

| 维度 | 至少覆盖的变化 | 为什么单一用例不够 |
| --- | --- | --- |
| 数值 | dtype、极值、归约长度、前向/梯度 | 误差随归约与训练步积累，逐位相同也未必是合理要求 |
| 形状 | 短/长序列、不整齐尺寸、不同 batch | 编译特化与访存尾部处理会改变路径 |
| 状态 | 随机数、optimizer、序列化/恢复 | 前向正确不能证明恢复后继续训练正确 |
| 执行 | eager、compile、混合精度、动态图 | 后端路径不同，不能共享一个“已通过”标志 |
| 分布式 | 单机、多机、不同并行组合、超时 | 会引入新的顺序关系与失败方式 |
| 升级 | 框架、编译器、驱动、通信库组合 | 每层分别兼容，不代表整组版本兼容 |

容差应按算子和业务目标设定，而不是所有 tensor 共用一个阈值。归约顺序变化本来就可能带来浮点差异；反之，一个看似很小的系统偏差，也可能经过多步训练影响最终结果。PyTorch 的[数值精度说明](https://docs.pytorch.org/docs/stable/notes/numerical_accuracy.html)适合用作建立预期的起点。

性能同样需要拆分。首轮编译耗时、稳态吞吐、显存峰值、尾延迟和失败恢复成本应分别记录。若一次优化用更长编译换取稳定 shape 下的高吞吐，它可能适合长时间训练，却不适合频繁换模型的短作业；这是工作负载的选择，不是“优化成功/失败”的二元结论。

## 六、上游化的价值是降低组合成本

一个后端可以暂时通过大量特判跑通模型，但特判越多，框架升级时越难判断行为变化来自哪里。上游化并不只是把代码放到某个公共仓库，而是让接口、测试、错误报告和维护责任进入可共同演进的边界。

对使用者而言，可维护性可以问得很具体：一个 graph break 能否生成最小复现？升级后是否有支持的版本组合？性能回退是否能定位到图、kernel 或通信路径？设备错误能否转换成框架理解的异常，而不是让作业无限等待？

评估新硬件时，可以先挑一个实际业务模型，按“单卡 eager → 单卡 compile → 多卡 → 故障/恢复 → 版本升级”的顺序测试。把每一步遇到的补丁、未支持路径和版本限制记下来，它们比一次跑通的演示更能反映后续维护量。
