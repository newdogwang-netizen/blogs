“GPU 利用率只有 30%”还不足以判断问题。它可能表示显存已被模型占满而计算间歇发生，也可能是一个大任务只用到了部分 SM，还可能只是夜间没有请求。曲线看起来相似，处理方法却不同。

大会的 HAMi 复盘提供了两个值得分开研究的案例：合合信息的 GPU 共享实践，以及招商银行的训练/推理潮汐调度。它们不是同一个系统的两段架构，企业效果也不是我们集群的收益保证。[项目官方复盘](https://project-hami.io/blog/kubecon-china-2026-recap)、[大会专题页](https://project-hami.io/landing/kubecon-china)

下面分别分析资源怎样共享、借出的容量怎样收回。容量数字用于算例，未在真实业务上压测。

## 一、把“浪费”拆成空间与时间

空间碎片指某个任务申请或独占的设备资源，大于它能有效使用的部分。例如多个小模型分别占用整卡，但它们各自的常驻显存和计算压力允许在受控条件下共存。

时间错配则是设备白天忙、夜间闲，或者在线任务为峰值预留的容量长时间没有被使用。此时即使单卡上的工作负载已经很紧凑，仍然可以考虑把闲时容量借给可中断工作。

{% include infra-figure.html file="gpu-two-wastes" alt="左侧展示同一时刻整卡分配产生的空间碎片，右侧展示不同时间的在线需求峰谷与可借用容量" caption="图 1 · 两类浪费的示意，不是业务监控数据。共享改变同一时刻的装载方式；潮汐改变容量在时间上的归属。" %}

这一区分决定第一步该采什么数据。空间问题需要每个工作负载的显存峰值、活跃计算区间和共置干扰；时间问题需要需求峰谷、扩容提前量和容量归还时间。只有一条整卡利用率平均线，无法推断任何一种方案是否安全。

## 二、空间共享的核心是资源约束能否兑现

HAMi 将异构设备资源声明、调度与共享执行机制连接起来。在其 NVIDIA 软件共享路径中，HAMi-core 通过 CUDA 调用拦截等方式实现相关资源控制；这和 MIG 的硬件分区不是同一层隔离。[HAMi-core 项目说明](https://github.com/Project-HAMi/HAMi-core)

“能够限制显存”与“所有错误都被隔离”尤其不能画等号。应用可见的配额、设备实际执行路径和驱动级故障范围应分别理解。还要测试程序是否使用覆盖范围之外的调用方式，以及所选 CUDA、驱动与框架版本组合是否受支持。

NVIDIA GPU time-slicing 也不能被自动理解成显存隔离：官方明确说明，这种共享方式不提供 MIG 那样的显存与故障隔离。MIG 则在受支持的设备与 profile 下提供硬件划分，但仍不是“每个租户拥有一整台独立服务器”。[GPU Operator 共享说明](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html)、[MIG 概念](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/introduction.html)

所以合合信息案例最值得借鉴的不是“把一张卡拆成几份”这个数字，而是工作负载画像如何进入分配模型：常驻显存小但突发强的服务，和显存稳定、计算长期饱和的作业，不应使用同一套共置假设。

## 三、动态 MIG 为什么需要调度器协作

固定切分容易出现“总空闲容量不少，却没有一个合适形状的分区”。假设现有布局偏向小实例，队列里突然来了需要较大 profile 的任务，小实例的空闲总和也不一定能直接满足它。

动态切分的目标是让布局与排队需求共同决策；大会 HAMi 相关分享讨论了这一方向。[大会专题与场次说明](https://project-hami.io/landing/kubecon-china) 但“动态”不应写成任意运行中的实例都能无损原地变形。具体重配置需要满足硬件、驱动与已有实例占用条件，可能涉及迁移、排空或重建。

从系统设计看，这会产生一个顺序问题：先调度任务，可能找不到合适实例；先改布局，又可能影响已有租户。合理的控制过程需要先确定受影响范围，阻止新的冲突分配，排空需要腾出的实例，完成重配置，再让资源库存反映新布局。

这是本文的控制面推导，不是声称所有 HAMi 版本都已经以完全相同的状态机实现。评估具体方案时，应要求看到布局转换失败与回退路径，而不仅是成功切分的演示。

## 四、时间共享的困难是按时归还容量

招商银行的分享涉及利用负载峰谷组织训练与推理容量，并讨论 KEDA、vLLM/LoRA 与 checkpoint 等相关环节。它提供的是业务场景与实现线索，不意味着把这些项目装在一起就自动获得潮汐平台。[官方复盘中的案例介绍](https://project-hami.io/blog/kubecon-china-2026-recap)

对在线业务而言，借出去多少卡不是最难的问题。真正的约束是：当请求回升，卡能否在延迟目标被打破前回到在线池。

{% include infra-figure.html file="gpu-capacity-return" alt="容量归还依次经过停止接收新离线工作、保存状态、释放设备、启动在线副本和验证服务容量" caption="图 2 · 建议的容量归还时序。监测到需求并不等于容量已经可用，必须计入整条链路的延迟。" %}

可将归还预算写成：`T归还 = T检测 + T排空/检查点 + T释放 + T在线启动 + T验证`。部分阶段能够重叠时，应按关键路径计算，而非机械求和；但任何一段都不能因为监控面板上已经出现扩容意图而被省略。

举一个算例：假设推理需求在 90 秒内快速上升，而离线作业安全保存需要 60 秒，随后模型加载和预热还要 50 秒。即使检测零延迟，完全依赖临时回收也赶不上这次上涨。解决方向可能是保留热容量、提前预测回收、缩短检查点路径，或者缩小可借出的份额。单纯把扩容阈值调得更敏感，只能改善检测那一段。

## 五、两个控制环叠加，可能相互放大

空间共享与时间共享可以结合，但不是收益简单相加。设在线推理与可中断训练共享一张卡：请求上升时，推理延迟增加，伸缩器准备增加副本；与此同时训练作业开始写 checkpoint，又消耗 CPU、存储和网络带宽，进一步拖慢新副本启动。

这时“扩容后延迟更高”不一定是模型异常，而可能是多个控制环争夺同一条启动路径。需要明确哪个信号触发回收，哪个控制器持有最终容量决定权，回收期间是否暂停新的共享装载，以及是否有冷却时间与最小驻留时间。

尤其要避免循环承诺：调度器认为共享能释放容量，所以准入更多任务；伸缩器又把这些任务的存在当作真实空闲减少，继续扩容；最后系统不停移动负载，没有稳定工作区间。

## 六、用有效产出验收收益

利用率只是一个过程指标。在线业务更关心在延迟和成功率约束下完成了多少有效请求，训练更关心单位时间得到多少有效进展。共享后 GPU 曲线变高，但超时重试、训练回滚和操作成本一起上升，经济上未必更好。

建议至少比较三组：独占基线、仅空间共享、空间共享加潮汐回收。使用相同的请求回放和离线工作量，记录在线 P95/P99、失败率、训练有效步、checkpoint 时间、归还时间分布与人工干预次数。不能只比较一次低峰演示与一次高峰基线。

还可以建立一个便于评审的指标：`单位有效产出成本 = 总 GPU 时间及配套成本 / 满足质量与 SLO 的有效工作量`。它不要求不同业务共用一个分母，但要求分母不能把失败重试也当作新增产出。

试点可以分两步：先测共置后在线请求的尾延迟，再测需求回升时的容量归还时间。如果第二步赶不上业务峰值，就需要保留热容量，或者减少可借出的卡数。这部分余量应计入方案成本，不能因为平时闲着就算作浪费。
