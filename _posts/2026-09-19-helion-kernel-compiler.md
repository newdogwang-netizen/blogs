同一个数学算子，在两种加速器上获得好性能，往往需要完全不同的执行组织：tile 大小、线程布局、共享内存、异步搬运和矩阵指令都可能变化。若每个算子都手写多份低层实现，维护成本会随硬件和 shape 组合迅速增长。

大会的 [Helion 新 CuTe DSL/Pallas 后端及 Agent 辅助开发分享](https://www.lfopensource.cn/kubecon-cloudnativecon-openinfra-summit-pytorch-conference-china/program/schedule/?id=1293054)讨论了提高 kernel 表达层次的路径。截至 2026-09-19，开发提交 **`0b66239`** 的后端注册表已包含 CuteBackend 与 PallasBackend。以下以这份源码为准；PyPI 发布版是否包含对应实现、支持哪些算子和硬件，需要另查该版本的说明。[固定提交的后端注册表](https://github.com/pytorch/helion/blob/0b662391e4079a1ed40ce141ed2f5d793f647d5d/helion/_compiler/backend_registry.py)

本文没有 GPU/TPU benchmark，所有性能例子只是分析方法。

## 一、数学表达和执行布局是两类决定

以矩阵乘为例，`C = A × B` 定义了结果，却没有定义一次处理多大的块，哪些线程协作读取，数据在寄存器和共享内存停留多久，也没有定义如何处理尾部不整齐尺寸。

高层 DSL 的目标不是让这些决定消失，而是把其中一部分从每个算子作者手里移到编译器和调优系统中。Helion 使用嵌入 Python 的 kernel 表达，结合代码生成与自动调优来寻找设备执行方案。[项目说明](https://github.com/pytorch/helion)

第二篇讨论的是整个异构软件栈，这里只看 kernel 的表达与 lowering：高层操作怎样逐步转换为目标设备的执行代码。框架运行时、自动微分和通信仍由其他层负责。

## 二、前端统一之后，后端仍然要理解硬件

{% include infra-figure.html file="helion-compiler-backends" alt="高层 Helion 表达进入公共分析和调优，再分别通过 Triton、CuTe DSL 与 Pallas 后端降低到目标设备；路径支持范围并不相同" caption="图 1 · 编译责任示意。三条路径表示不同后端，不表示任意 kernel 可以无条件在三者间切换。" %}

后端承担的不是简单改写语法。它需要把迭代、归约、访存和布局映射到目标执行模型。相同操作在一个后端可能有直接高效的原语，在另一个后端则需要分解，或根本暂不支持。

固定提交的 registry 将后端查找、实例化与相应代码生成模块的注册集中管理。这个结构值得关注：增加后端应尽量扩展明确的后端边界，而不是把每个前端操作都写成越来越长的硬件条件分支。[注册与加载代码](https://github.com/pytorch/helion/blob/0b662391e4079a1ed40ce141ed2f5d793f647d5d/helion/_compiler/backend_registry.py)

但良好的扩展点只减少组织成本，不自动带来等价语义。访存顺序、原子操作、归约精度、索引边界和布局转换，每一项仍需要后端测试。尤其要避免只验证一个整齐 shape：尾块处理常常是高性能路径之外最容易出错的地方。

## 三、自动调优在搜索什么

自动调优可以搜索 tile、并行划分与相关执行参数。不同选项影响资源占用和数据复用：更大的 tile 可能减少重复读取，也可能增加寄存器压力；更多流水阶段可能隐藏访存延迟，也可能占用更多片上存储。

因此，调优不是“参数越大越快”，而是在资源约束下寻找合适的组合。固定 shape 的最佳配置，也不一定适合另一种 batch 或序列长度。需要把 shape 分布纳入目标，而非只优化一张 benchmark 表中的单元格。

调优还有时间成本。假设搜索耗时 120 秒，每次调用节省 20 微秒，忽略其他成本，至少需要约 600 万次调用才能摊平搜索时间。这是算例，不是 Helion 的实测开销。对长时间稳定运行的服务，预调优和缓存可能合理；对短作业，首次运行延迟可能更重要。

## 四、性能可移植性不能只看“都能编译”

“源代码可复用”“结果正确”“在每种硬件上都接近各自强基线”是三个不同目标。前两个通过后，才有资格讨论第三个。

建议按 shape、dtype、布局和硬件做矩阵验证。每个格子同时记录是否支持、数值误差、编译时间、稳态时间与内存占用；没有跑过的格子标为未验证，而不是用另一硬件的结果填补。

还要看端到端占比。若一个算子占应用时间的 10%，把它加速两倍，忽略其他变化，整体加速约为 `1 / (0.9 + 0.1 / 2) ≈ 1.053`，即约 5.3%。kernel 层的漂亮数字，不能直接当作服务吞吐提升。

## 五、Agent 生成的实现，怎样独立验证

大会标题把 Agent 辅助后端开发放到了显眼位置。它提示一种开发方式：让 Agent 帮助生成 lowering、测试和候选优化，再通过编译器和运行结果反馈迭代。但 Agent 生成得快，不会降低正确性标准。

{% include infra-figure.html file="helion-verification-loop" alt="候选实现先通过编译和数值测试，再接受性能测试与跨形状回归；失败回到候选阶段，只有证据齐全才进入发布" caption="图 2 · 建议的生成—验证闭环。性能测试不能替代数值测试；测试集合也需要独立于被优化实现。" %}

一个危险的闭环是：Agent 同时修改实现、参考答案和测试容差，然后宣布通过。更可靠的做法是保护独立 oracle，保存固定回归输入，让候选实现只能在明确范围内修改。对低精度算子，容差应事先根据数值特性制定，而不是在失败后不断放宽。

性能测试也需要防止“优化测试而非优化算子”：忽略输入变化、缓存固定输出、跳过某种边界尺寸，都会制造看似很快但无效的结果。生成代码与人工代码应经过相同审查。

## 六、什么时候值得引入

如果团队需要维护多种硬件上的一组热点算子，并有稳定的正确性与性能测试基础，可以尝试高层表达和多后端编译。若问题主要是模型调度、网络或 CPU 数据处理，换一种 kernel DSL 很可能不在关键路径上。

实践起点可以很小：选一个已被 profile 证明昂贵的算子，固定参考实现、输入分布和硬件；完成一个后端的正确性与性能对照，再扩展到第二个。这样才能分辨收益来自高层表达、调优搜索，还是只是某个特别合适的测试形状。

第二个后端接入后，再回头统计有多少代码能够共用、有多少测试需要重写、每次升级要花多少调优时间。这些维护成本和稳态性能一样，决定了采用多后端方案是否划算。
